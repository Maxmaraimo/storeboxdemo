# Совместная работа над StoreBox

`main` — общая ветка проекта. Каждый разработчик работает в своей короткоживущей
ветке и предлагает изменения через Pull Request (PR). Не коммитьте напрямую в
`main`, не используйте `git push --force` для общих веток и не копируйте файлы
из одной рабочей папки поверх другой.

## Начало задачи

```bash
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feature/kratkoe-nazvanie
```

Держите в одной ветке одну задачу. Перед коммитом проверьте `git status` и
`git diff`, добавляйте в коммит только относящиеся к задаче файлы. Не добавляйте
`.env`, ключи, базу данных, медиа, браузерные профили, `node_modules` или
результаты сборки.

## Передача изменений другому разработчику

```bash
git add <нужные-файлы>
git commit -m "Краткое описание изменения"
git push -u origin feature/kratkoe-nazvanie
```

Откройте PR в `main`: опишите изменение, проверку и возможные последствия для
деплоя. Второй разработчик проверяет PR; после одобрения и успешных проверок
ветка вливается в `main`. Если `main` обновился до слияния, подтяните его в
свою ветку и разрешите конфликты осознанно:

```bash
git fetch origin
git switch feature/kratkoe-nazvanie
git merge origin/main
```

Не сбрасывайте чужие коммиты ради разрешения конфликта. После слияния каждый
разработчик обновляет свой `main` через `git pull --ff-only origin main` и
создаёт новую ветку для следующей задачи. Для защиты от случайной публикации
владельцу GitHub-репозитория следует включить защиту `main`: обязательный PR,
хотя бы одно одобрение и запрет force push.

## Деплой

Публикуйте только проверенный коммит из объединённого `main`, записывая его
SHA. Перед выкладкой сохраняйте резервную копию и проверяйте миграции и тесты.
Серверные `.env`, базу данных и `media` не заменяйте файлами из репозитория.
Не запускайте корневой `deploy.sh`: в `DEPLOYMENT_VDS.md` описано, почему он
не подходит для действующего сервера.

**Перед следующим деплоем:** на сервере есть изменения, которых пока нет в
GitHub. Их нужно сохранить как коммиты или патчи, сравнить с текущим `main` и
внести через отдельный PR. До этого выкладка `main` может стереть последние
изменения интерфейса. Не делайте `git reset --hard` и не перезаписывайте
рабочую копию на сервере, пока эти изменения не сохранены.

В репозитории уже отслеживаются некоторые сгенерированные файлы и зависимости.
Очистку их из Git нужно делать отдельным проверенным PR, не смешивая с
функциональными изменениями или срочным деплоем.
